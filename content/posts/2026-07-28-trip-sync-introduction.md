# TRIP SYNC：從旅行人格開始，把靈感變成走得動的行程

`TRIP SYNC` 是一個以「旅行人格」為入口的旅遊內容網站。

網站連結：[https://chienchien6.github.io/trip-sync-quiz/](https://chienchien6.github.io/trip-sync-quiz/)

它不是單純列出熱門景點，也不是把目的地排成必去清單，而是先理解使用者的旅行節奏、預算、交通方式、避雷條件與探索風格，再把這些線索整理成更容易執行的旅行建議。

我喜歡它的地方是，它把旅行規劃從「想去哪裡」往前推了一步，變成「我適合怎麼旅行」。

## 網站想回答的問題

很多旅遊內容會直接告訴你哪裡好玩，但真正規劃時，卡住的往往不是景點名稱，而是更日常的選擇。

例如：

- 這個目的地適合第一次去的人嗎？
- 如果不想行程太累，哪些安排要刪掉？
- 住宿區域會不會影響交通成本？
- 這個季節去會不會踩雷？
- 預算看起來夠，但哪些隱形支出容易被低估？
- 這個地方適合慢慢散步，還是適合高效率踩點？

TRIP SYNC 想做的是把這些判斷整理成內容，而不是只給一串景點。

## 旅行人格測驗

網站的一個入口是旅行人格測驗。

測驗用情境題讓使用者理解自己偏好的旅行模式，例如喜歡鬆散探索還是緊湊行程、重視預算控制還是體驗完整度、習慣大眾運輸還是願意轉乘移動。

這種入口比直接搜尋目的地更有趣，因為使用者會先看見自己的旅行習慣，再回頭理解哪些城市、路線或文章適合自己。

它也讓旅遊內容有更清楚的分眾方式。不是每篇文章都要服務所有人，而是可以針對不同旅行人格提供更貼近的建議。

## 旅行指南文章

TRIP SYNC 的另一個重點是旅行指南文章。

這些文章不是只寫心得，而是希望把目的地寫成真的可以規劃的路線。內容會結合：

- 個人實地經驗
- 官方資料查核
- 預算判斷
- 交通方式
- 季節提醒
- 住宿與路線選擇
- 檢查清單
- 資料來源
- 相關文章

這樣的設計讓文章比較像「規劃工具」，不是單純遊記。

我也很喜歡 README 裡提到的一點：文章會保留個人實地經驗，但也會標出資料來源，讓讀者知道哪些是親身體驗，哪些需要出發前再回官方網站確認。

這種界線很重要。旅遊資訊常常會過期，尤其是交通、票價、營業時間與預約規則。把資訊來源標出來，比假裝所有內容永遠正確更負責任。

## 本機內容後台

TRIP SYNC 也做了一個本機內容後台，可以新增、編輯、刪除和排序文章。

指南文章資料儲存在：

```text
src/data/guides.json
```

後台支援草稿和已發布狀態，圖片可以上傳到：

```text
public/guide-covers
public/guide-images
```

它的內容更新流程很清楚：

```text
打開後台 → 修改文章 → 按「儲存全部」→ commit → push
```

線上部署在 GitHub Pages，所以線上後台不能直接寫回 repo。正式內容更新仍然是在本機後台儲存後，透過 Git commit 和 push 發布。

這個限制反而讓內容流程很穩定。它適合個人或小型內容網站，不需要一開始就接大型 CMS，也能保留版本控制。

## 技術筆記

TRIP SYNC 使用：

- Vue 3
- Vite
- TypeScript
- GitHub Pages
- GitHub Actions

推送到 `main` 後，GitHub Actions 會自動建置並部署到 GitHub Pages。部署流程定義在：

```text
.github/workflows/deploy-pages.yml
```

前台和後台都在同一個單頁網站裡，後台路徑使用：

```text
/#/admin
```

這樣的架構很適合靜態內容網站。前台可以被 GitHub Pages 服務，內容資料則由 JSON 和圖片資料夾管理。

## 我喜歡這個作品的地方

TRIP SYNC 最有意思的地方，是它沒有把旅行內容當成資訊堆疊，而是當成一種「選擇的整理」。

旅行規劃其實不只是找景點。真正困難的是在有限時間、有限體力、有限預算裡，決定什麼值得去、什麼可以放掉、什麼要提前確認。

旅行人格測驗讓這件事變得比較容易開始。旅行指南文章則把靈感落地成可以執行的路線。

對我來說，這個網站的方向不是告訴所有人「你一定要去這裡」，而是幫讀者找到「這樣旅行比較適合你」。
